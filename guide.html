Construire un chart Helm, déployé par ArgoCD sur EKS

Vous allez écrire vous-même un chart Helm, composant par composant. À chaque ajout que vous poussez sur Git, ArgoCD met le cluster à jour automatiquement : vous voyez votre application grandir. Objectif : comprendre le GitOps, écrire des manifests Kubernetes et découvrir Helm.

🧭 Deux environnements, deux rôles
AWS CloudShell pour tout ce qui touche AWS et le cluster (créer l'EKS, installer ArgoCD, kubectl). Authentifié sur la sandbox : aucun risque pour un compte d'entreprise.
Poste local (IDE) pour écrire le code (le chart Helm), helm lint et git. On n'y lance jamais de commande AWS.
Introduction

Ce que vous allez construire

  • Un cluster EKS (Kubernetes managé), créé en une commande.
  • ArgoCD installé dessus : l'agent GitOps.
  • Un chart Helm podinfo que vous écrivez pas à pas — Deployment, Service, paramétrage, sondes de santé, autoscaling (HPA).
⏱️ Pas de course
L'atelier n'est pas chronométré au cordeau : si vous ne finissez pas en séance, le guide est autonome — vous pourrez terminer chez vous. Des indices repliés vous aident à chaque étape d'écriture (à n'ouvrir qu'en cas de blocage).

Étape 1CloudShell · ~15-20 min

Créer le cluster EKS

CloudShell On lance la création tout de suite (elle prend 15-20 min), puis on enchaîne sur la théorie pendant que ça provisionne.

1. Poser le fichier cluster.yaml

cat > cluster.yaml <<'EOF'
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig
metadata:
  name: atelier-argocd
  region: us-east-1
  version: "1.34"
managedNodeGroups:
  - name: ng-atelier
    instanceType: t3.medium
    desiredCapacity: 2
    minSize: 2
    maxSize: 2
    volumeSize: 20
    ssh:
      allow: false
EOF
cat cluster.yaml
⚠️ Version EKS
La version doit être en « standard support ». Si eksctl refuse 1.34, il affiche les versions valides du jour — reprenez-en une (ex. 1.33 si encore supportée, sinon la plus récente proposée).

2. Lancer la création

eksctl create cluster -f cluster.yaml
💡 Si CloudShell se déconnecte
La création continue côté AWS (CloudFormation). Rouvrez CloudShell, recollez le bloc cluster.yaml, puis aws eks update-kubeconfig --name atelier-argocd --region us-east-1.
Étape 2pendant la création

Théorie : Kubernetes, GitOps, Helm

Kubernetes en 2 minutes

Kubernetes orchestre des conteneurs à partir d'un état souhaité décrit en YAML. Objets clés : Pod (conteneur(s)), Deployment (répliques + mises à jour), Service (adresse stable), Namespace (cloisonnement).

GitOps & ArgoCD

Le GitOps fait de Git la source de vérité : un agent (ArgoCD) réconcilie en continu le cluster avec un dépôt. Vous committez → ArgoCD synchronise. Retour arrière = git revert.

Helm : le gestionnaire de paquets Kubernetes

Un chart Helm est un paquet de manifests templatés. Structure :

  • Chart.yaml : métadonnées (nom, version).
  • values.yaml : les valeurs (paramètres) par défaut.
  • templates/ : les manifests, où l'on injecte les valeurs avec {{ .Values.xxx }}.

Intérêt : un même chart, des valeurs différentes → pas de copier-coller de YAML.

Étape 5CloudShell → local

Accéder aux interfaces (ArgoCD & podinfo)

CloudShell ne permet pas d'ouvrir un port dans le navigateur. On génère donc, dans CloudShell, un kubeconfig portable (authentifié par un jeton, sans AWS), qu'on utilise en local pour faire les port-forward et ouvrir les UIs.

CloudShell — créer le jeton d'accès

echo "=== ServiceAccount + droits (TP éphémère : droits larges) ==="
kubectl -n argocd create serviceaccount atelier-viewer
kubectl create clusterrolebinding atelier-viewer \
  --clusterrole=cluster-admin \
  --serviceaccount=argocd:atelier-viewer

1) D'abord, récupérer les trois valeurs (serveur, certificat, jeton) dans des variables :

echo "=== Recuperer serveur, certificat et jeton (24h, sans AWS) ==="
SERVER=$(kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}')
CA=$(kubectl config view --minify --flatten -o jsonpath='{.clusters[0].cluster.certificate-authority-data}')
TOKEN=$(kubectl -n argocd create token atelier-viewer --duration=24h)

echo "SERVER  = $SERVER"
echo "CA      = ${#CA} caracteres"
echo "TOKEN   = ${#TOKEN} caracteres"
⚠️ Vérifiez avant de continuer
Les trois lignes echo doivent afficher un SERVER en https://…eks.amazonaws.com et des longueurs non nulles pour CA et TOKEN. Si l'une est vide, relancez la commande correspondante avant de passer à la suite.

2) Ensuite, générer le fichier kubeconfig. Collez ce bloc seul (sa première ligne cat > atelier-kubeconfig.yaml <<EOF ne doit rien avoir avant elle) :

cat > atelier-kubeconfig.yaml <<EOF
apiVersion: v1
kind: Config
clusters:
- name: atelier-argocd
  cluster:
    server: $SERVER
    certificate-authority-data: $CA
contexts:
- name: atelier
  context:
    cluster: atelier-argocd
    user: atelier-viewer
    namespace: argocd
current-context: atelier
users:
- name: atelier-viewer
  user:
    token: $TOKEN
EOF
echo "Fichier atelier-kubeconfig.yaml cree."
⚠️ Collage du heredoc (Safe Paste)
Confirmez le « Safe Paste » (bouton Paste). Après le collage, regardez la première ligne dans l'invite : elle doit se terminer par <<EOF. Si elle s'arrête à < (le <<EOF a été coupé), faites Ctrl+C et recollez uniquement ce bloc. Le heredoc utilise <<EOF sans quotes pour que $SERVER, $CA, $TOKEN soient remplacés par leurs valeurs.

3) Vérifier que le fichier contient bien les vraies valeurs (et pas $SERVER) :

echo "=== Verification du kubeconfig genere ==="
head -12 atelier-kubeconfig.yaml

CloudShell — télécharger le fichier

Menu Actions → Download file, saisissez atelier-kubeconfig.yaml.

Poste local — utiliser le kubeconfig (sans AWS)

Placez le fichier dans un dossier local (ex. .local/ du dépôt, ignoré par git). Puis, dans le terminal local :

export KUBECONFIG=.local/atelier-kubeconfig.yaml
kubectl get nodes
✅ Checkpoint
get nodes renvoie les 2 nœuds — depuis votre poste, sans commande AWS. export KUBECONFIG n'affecte pas votre ~/.kube/config habituel.

Poste local — ouvrir l'UI ArgoCD

Identifiants de connexion à l'UI ArgoCD :

  • Utilisateur : admin — c'est le compte administrateur créé par défaut à l'installation d'ArgoCD (rien à récupérer, c'est toujours admin).
  • Mot de passe : généré automatiquement, stocké dans le secret argocd-initial-admin-secret. Récupérez-le (en local, le kubeconfig est chargé) :
echo "=== Mot de passe admin ArgoCD (utilisateur : admin) ==="
kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath="{.data.password}" | base64 -d ; echo ""
💡 Notez ce mot de passe
Copiez-le : vous en aurez besoin pour vous connecter juste après. Ne le partagez pas.

Ouvrez ensuite le tunnel vers l'UI (laissez-le tourner) :

kubectl port-forward svc/argocd-server -n argocd 8080:443

Ouvrez https://localhost:8080 (acceptez l'avertissement de certificat auto-signé) et connectez-vous avec admin + le mot de passe ci-dessus. Laissez le tunnel tourner ; ouvrez un 2ᵉ terminal pour la suite (avec export KUBECONFIG à nouveau).

Étape 6local + GitHub

Fork & Application ArgoCD

ArgoCD déploie un chart Helm depuis un dépôt Git. Vous allez forker le dépôt de l'atelier, puis déclarer une Application qui pointe vers charts/podinfo de votre fork.

Forker

Sur GitHub, cliquez Fork. Notez l'URL de votre fork (https://github.com/<VOTRE-COMPTE>/<VOTRE-REPO>.git, visible via le bouton Code → onglet HTTPS de votre fork). Le dépôt contient déjà un squelette de chart : charts/podinfo/Chart.yaml, values.yaml, et un dossier templates/ vide — c'est vous qui le remplirez.

Poste local — déclarer l'Application

Votre fork contient déjà le fichier argocd/application.yaml. Ouvrez-le dans votre IDE et remplacez la ligne repoURL par l'URL de votre fork :

⚠️ Remplacez l'URL du dépôt
Dans argocd/application.yaml, remplacez toute l'URL repoURL par celle de votre fork (compte ET nom de repo peuvent différer), puis enregistrez.

Appliquez ensuite l'Application (le kubeconfig est chargé depuis l'étape 5, donc en local, sans AWS) :

export KUBECONFIG=.local/atelier-kubeconfig.yaml
kubectl apply -f argocd/application.yaml
kubectl -n argocd get applications
✅ Checkpoint
L'application podinfo apparaît en Synced / Healthy, mais rien n'est déployé : le dossier templates/ est vide, donc Helm ne rend aucun manifest. Le namespace podinfo n'est pas encore créé — il le sera au premier template ajouté (étape 7). C'est normal. Rafraîchissez l'UI ArgoCD (le tunnel de l'étape 5, https://localhost:8080) pour voir apparaître l'application.

Poste local — déclarer l'Application Kubernetes Dashboard (+ metrics-server)

Avant Prometheus, on ajoute une Application ArgoCD qui déploie le Kubernetes Dashboard : l'UI web officielle qui donne une vue complète du cluster. On y consulte, sans quitter le navigateur :

  • Workloads : Deployments, ReplicaSets, StatefulSets, DaemonSets, Jobs/CronJobs, et l'état des Pods (Running / Pending / CrashLoopBackOff, nombre de redémarrages, nœud d'affectation, âge).
  • Métriques CPU / RAM par nœud, namespace, pod et conteneur (graphiques d'évolution) — grâce au metrics-server.
  • Events : idéal pour diagnostiquer un pod bloqué (ImagePullBackOff, OOMKilled, échec de probe readiness/liveness…).
  • Logs et exec (shell) dans un conteneur, directement depuis l'UI.
  • Config (ConfigMaps, Secrets — contenu masqué, variables d'environnement injectées), réseau (Services, Endpoints, Ingress) et stockage (PVC/PV, StorageClasses).

L'Application installe aussi le metrics-server (l'API metrics.k8s.io) qui alimente les graphiques CPU/RAM. Le reste des informations (workloads, events, logs…) provient directement de l'API Kubernetes, sans metrics-server.

💡 Utile pour l'atelier
Pendant l'étape 7, gardez le Dashboard ouvert : vous verrez podinfo se construire au fil des commits — le Deployment apparaître, le Pod passer Running, ses logs et ses probes, puis le HPA scaler selon la charge CPU.
💡 Pourquoi metrics-server ?
EKS n'installe pas le metrics-server par défaut. Sans lui, le Dashboard s'affiche (workloads, events, logs…) mais les graphiques CPU/RAM restent vides (et kubectl top ne fonctionne pas). Le fichier argocd/dashboard.yaml déploie les deux, ordonnés par sync-wave (metrics-server d'abord, Dashboard ensuite).
💡 Dépôts publics — rien à personnaliser
Comme l'Application monitoring, cette Application pointe vers des dépôts Helm publics — rien à personnaliser dans argocd/dashboard.yaml.

Le fichier argocd/dashboard.yaml est déjà dans votre fork. Appliquez-le :

export KUBECONFIG=.local/atelier-kubeconfig.yaml
kubectl apply -f argocd/dashboard.yaml
kubectl -n argocd get applications

Une fois les applications Synced / Healthy, ouvrez le Dashboard via un port-forward (approche cohérente avec le tunnel de l'étape 5). Le Dashboard v7 s'expose via le proxy Kong sur le port 443 (HTTPS) :

export KUBECONFIG=.local/atelier-kubeconfig.yaml
kubectl -n kubernetes-dashboard port-forward svc/kubernetes-dashboard-kong-proxy 8443:443

Puis ouvrez https://localhost:8443 (acceptez l'avertissement de certificat auto-signé). Le Dashboard demande un token : créez un compte de service admin (pour l'atelier) et générez un token éphémère :

export KUBECONFIG=.local/atelier-kubeconfig.yaml

# Compte de service + droits admin (contexte atelier uniquement)
kubectl create serviceaccount dashboard-admin -n kubernetes-dashboard
kubectl create clusterrolebinding dashboard-admin \
  --clusterrole=cluster-admin \
  --serviceaccount=kubernetes-dashboard:dashboard-admin

# Générer un token (valable ~1h) à coller dans l'UI
kubectl -n kubernetes-dashboard create token dashboard-admin
⚠️ Droits admin — contexte atelier
Le rôle cluster-admin donne un accès complet. C'est acceptable dans la sandbox jetable de l'atelier, mais à éviter sur un vrai cluster : on y créerait un rôle restreint (lecture seule, namespace ciblé).
✅ Checkpoint
Les applications metrics-server et kubernetes-dashboard sont Synced / Healthy. Dans l'UI, explorez :
  • Workloads → Pods : statut, redémarrages, et après ~1 min (collecte metrics-server) les graphiques CPU / mémoire.
  • Cluster → Nodes : utilisation CPU/RAM par nœud.
  • Ouvrez un pod → onglets Logs et Events.
En ligne de commande, kubectl top nodes et kubectl top pods -A renvoient aussi des valeurs.

Poste local — déclarer l'Application Prometheus (monitoring)

On ajoute une seconde Application ArgoCD qui déploie Prometheus (kube-prometheus-stack, profil allégé, sans Alertmanager) depuis le dépôt Helm public de la communauté Prometheus. Elle servira à collecter les métriques du cluster et de podinfo (étape 7.6).

💡 Deux sources différentes
L'Application podinfo pointe vers votre fork (chart que vous écrivez). L'Application monitoring pointe vers un dépôt Helm public — rien à personnaliser dans argocd/monitoring.yaml.

Le fichier argocd/monitoring.yaml est déjà dans votre fork. Appliquez-le :

export KUBECONFIG=.local/atelier-kubeconfig.yaml
kubectl apply -f argocd/monitoring.yaml
kubectl -n argocd get applications
⚠️ Première synchro un peu longue
kube-prometheus-stack installe des CRDs et plusieurs composants (operator, Prometheus, node-exporter, kube-state-metrics). La 1ʳᵉ synchro peut prendre quelques minutes et passer transitoirement par Progressing / OutOfSync — c'est normal. L'option ServerSideApply=true (déjà dans le fichier) évite l'erreur « annotation too long » due aux CRDs volumineuses.
✅ Checkpoint
L'application monitoring finit en Synced / Healthy. kubectl get pods -n monitoring montre les pods Prometheus (operator, prometheus, exporters) en Running.

Construire le chart pas à pas

Pour chaque composant : vous écrivez le fichier dans votre IDE, validez avec helm lint charts/podinfo, visualisez le YAML généré avec helm template podinfo charts/podinfo, puis committez (IDE ou interface web GitHub). ArgoCD synchronise et vous observez le résultat (UI ArgoCD + kubectl).

7.1 — Le Deployment (templates/deployment.yaml)

🎯 Objectif
Créer charts/podinfo/templates/deployment.yaml : un Deployment de {{ .Values.replicaCount }} réplique(s) de l'image podinfo (paramétrée via values.yaml), exposant le port 9898, avec des requests CPU (nécessaires plus tard pour le HPA).
💡 Indice 1 — par où commencer

Un Deployment standard : apiVersion: apps/v1, kind: Deployment, un selector et un template de pod avec un conteneur. Le nombre de répliques vient de {{ .Values.replicaCount }}.

💡 Indice 2 — la syntaxe Helm clé

Pour l'image : image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}". Pour les ressources : cpu: {{ .Values.resources.requests.cpu }}. Le port container est 9898 (nommez-le http).

✅ Solution complète 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: podinfo
  labels:
    app: podinfo
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: podinfo
  template:
    metadata:
      labels:
        app: podinfo
    spec:
      containers:
        - name: podinfo
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          ports:
            - name: http
              containerPort: 9898
          resources:
            requests:
              cpu: {{ .Values.resources.requests.cpu }}
              memory: {{ .Values.resources.requests.memory }}
            limits:
              cpu: {{ .Values.resources.limits.cpu }}
              memory: {{ .Values.resources.limits.memory }}

Ajoutez les valeurs manquantes dans values.yaml :

resources:
  requests:
    cpu: 50m
    memory: 32Mi
  limits:
    cpu: 200m
    memory: 128Mi
✅ Après commit
Dans l'UI ArgoCD, un Deployment et un Pod podinfo apparaissent (kubectl get pods -n podinfo le confirme).

7.2 — Le Service (templates/service.yaml)

🎯 Objectif
Exposer podinfo dans le cluster via un Service ClusterIP sur le port 9898.
💡 Indice 1 — par où commencer

kind: Service, type: ClusterIP, un selector qui cible app: podinfo.

💡 Indice 2 — le port

port: 9898 et targetPort: http (le nom du port défini dans le Deployment).

✅ Solution complète 
apiVersion: v1
kind: Service
metadata:
  name: podinfo
  labels:
    app: podinfo
spec:
  type: ClusterIP
  selector:
    app: podinfo
  ports:
    - name: http
      port: 9898
      targetPort: http
✅ Après commit
local kubectl port-forward svc/podinfo -n podinfo 9898:9898, puis http://localhost:9898 : l'UI podinfo s'affiche.

7.3 — Paramétrer l'UI (message & couleur)

🎯 Objectif
Rendre le message et la couleur de l'UI configurables via values.yaml, injectés en variables d'environnement dans le Deployment. C'est le cœur de Helm.

💡 podinfo est une 12-factor app : ses options se configurent par variables d'environnement. La liste des paramètres (dont ui.message et ui.color) est documentée dans le README du chart podinfo officiel.
💡 Indice 1 — côté values

Ajoutez dans values.yaml un bloc ui: avec deux clés pour le message et la couleur. Les noms exacts et leurs valeurs par défaut sont dans le tableau « Configuration » du README du chart podinfo (cherchez ui.message et ui.color).

💡 Indice 2 — côté deployment

Avec viper (la lib de config de podinfo), chaque option --xxx-yyy se pilote aussi par la variable d'environnement PODINFO_XXX_YYY (majuscules, préfixe PODINFO_, tirets → underscores). Déduisez-en les deux variables pour le message et la couleur, puis ajoutez un bloc env: au conteneur, valorisé par {{ .Values.ui.message }} / {{ .Values.ui.color }}.

✅ Solution complète

values.yaml — ajoutez :

ui:
  message: "Bienvenue a l'atelier GitOps !"
  color: "#d97706"

templates/deployment.yaml — ajoutez sous le conteneur (après ports:) :

          env:
            - name: PODINFO_UI_MESSAGE
              value: "{{ .Values.ui.message }}"
            - name: PODINFO_UI_COLOR
              value: "{{ .Values.ui.color }}"
✅ Après commit — moment GitOps
Rafraîchissez podinfo : le message/couleur changent. Modifiez values.yaml, committez, et regardez ArgoCD resynchroniser puis l'UI se mettre à jour. Vous n'avez touché qu'à Git.

7.4 — Sondes de santé (readiness & liveness)

🎯 Objectif
Ajouter des sondes livenessProbe et readinessProbe au conteneur pour que Kubernetes gère proprement la santé du pod.
💡 Indice 1 — les endpoints

podinfo expose deux routes HTTP dédiées aux sondes Kubernetes (une pour la liveness, une pour la readiness). Leurs chemins sont listés dans la section « Web API » du README podinfo (cherchez « liveness probe » et « readiness probe »). Elles répondent sur le port http.

💡 Indice 2 — la forme

Chaque probe est un httpGet avec path et port: http, plus initialDelaySeconds / periodSeconds.

✅ Solution complète

templates/deployment.yaml — ajoutez au conteneur :

          livenessProbe:
            httpGet:
              path: /healthz
              port: http
            initialDelaySeconds: 5
            periodSeconds: 10
          readinessProbe:
            httpGet:
              path: /readyz
              port: http
            initialDelaySeconds: 5
            periodSeconds: 10
✅ Après commit
kubectl describe pod -n podinfo … montre les probes. Le pod reste Ready.

7.5 — Autoscaling (HPA)

🎯 Objectif
Ajouter un HorizontalPodAutoscaler qui ajuste le nombre de pods (1 à 5) selon le CPU. Créez templates/hpa.yaml et les valeurs hpa dans values.yaml.
💡 Indice 1 — l'API

L'objet s'appelle HorizontalPodAutoscaler. La version d'API stable et complète (permettant les métriques CPU/mémoire personnalisées) est autoscaling/v2 — voir la doc Kubernetes du HPA. Il cible le Deployment via un champ scaleTargetRef.

💡 Indice 2 — la métrique

La cible est une métrique Resource sur cpu, en Utilization (pourcentage moyen). La structure exacte (metrics → resource → target) est illustrée dans la walkthrough HPA. ⚠️ Deux prérequis : les requests CPU du Deployment (ajoutées en 7.1, sinon le HPA ne peut pas calculer le %) et le metrics-server (déjà présent sur EKS).

✅ Solution complète

values.yaml — ajoutez :

hpa:
  enabled: true
  minReplicas: 1
  maxReplicas: 5
  targetCPUUtilizationPercentage: 50

templates/hpa.yaml :

{{- if .Values.hpa.enabled }}
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: podinfo
  labels:
    app: podinfo
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: podinfo
  minReplicas: {{ .Values.hpa.minReplicas }}
  maxReplicas: {{ .Values.hpa.maxReplicas }}
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: {{ .Values.hpa.targetCPUUtilizationPercentage }}
{{- end }}
✅ Après commit
kubectl get hpa -n podinfo montre le HPA (cible CPU, min/max). Au repos il reste à 1 pod — c'est normal.

7.6 — Exposer podinfo à Prometheus (templates/servicemonitor.yaml)

🎯 Objectif
podinfo expose déjà ses métriques au format Prometheus sur /metrics (port http, 9898). Créez charts/podinfo/templates/servicemonitor.yaml : un ServiceMonitor qui dit à Prometheus (installé à l'étape 6) de scraper le Service podinfo. Ajoutez la valeur serviceMonitor.enabled dans values.yaml.
🔎 ServiceMonitor, c'est quoi ?
C'est une CRD installée par l'operator Prometheus (Application monitoring). Prometheus la détecte automatiquement (les sélecteurs du stack sont ouverts) et se met à collecter l'endpoint /metrics ciblé. Pas besoin de toucher à la config de Prometheus : tout est déclaratif, en GitOps.
💡 Indice 1 — l'API et la cible

apiVersion: monitoring.coreos.com/v1, kind: ServiceMonitor. Un selector.matchLabels qui cible app: podinfo (les mêmes labels que votre Service).

💡 Indice 2 — l'endpoint

Sous endpoints:, référencez le port par son nom (port: http, celui défini dans le Deployment/Service), path: /metrics, et un interval de scrape (ex. 15s). Entourez le tout d'un {{- if .Values.serviceMonitor.enabled }} comme pour le HPA.

✅ Solution complète

values.yaml — ajoutez :

serviceMonitor:
  enabled: true

templates/servicemonitor.yaml :

{{- if .Values.serviceMonitor.enabled }}
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: podinfo
  labels:
    app: podinfo
spec:
  selector:
    matchLabels:
      app: podinfo
  endpoints:
    - port: http
      path: /metrics
      interval: 15s
{{- end }}
✅ Après commit — observer les métriques
Ouvrez l'UI de Prometheus (port-forward local, dans un terminal avec export KUBECONFIG) : 
kubectl port-forward svc/prometheus-operated -n monitoring 9090:9090
Puis http://localhost:9090 → onglet Graph. Dans Status → Targets, la cible podinfo apparaît en UP. Testez une requête, p. ex. http_requests_total ou process_cpu_seconds_total{namespace="podinfo"}. Vous avez construit un chart Helm complet, scrapé par Prometheus, le tout en GitOps. 🎉

7.7 — (Bonus) Observabilité avec Dynatrace, en complément de Prometheus

🎯 Objectif
Ajouter Dynatrace comme plateforme d'observabilité, en plus de Prometheus (option A) : déployer le Dynatrace Operator via ArgoCD, puis un DynaKube qui connecte le cluster à votre tenant Dynatrace. Prometheus et le ServiceMonitor (7.6) restent en place.
⚠️ Prérequis spécifiques à cette étape (bonus, optionnel)
Contrairement au reste de l'atelier (100 % dans la sandbox), Dynatrace exige un compte externe :
  • Un tenant Dynatrace — essai gratuit 15 jours. Il vous donne un environment ID et l'URL https://<ENVIRONMENTID>.live.dynatrace.com.
  • Deux tokens générés dans l'UI Dynatrace (voir Tokens & permissions) : un operator token (apiToken) et un data ingest token (dataIngestToken).
Si vous n'avez pas de tenant, sautez cette étape : l'atelier est complet sans elle.

CloudShell — créer le namespace et le Secret des tokens

Le Secret contient des jetons sensibles : il ne doit jamais être commité dans votre fork public. On le crée donc à la main, hors GitOps (dans CloudShell, ou en local avec le kubeconfig chargé) :

kubectl create namespace dynatrace
kubectl -n dynatrace create secret generic dynakube \
  --from-literal="apiToken=<OPERATOR_TOKEN>" \
  --from-literal="dataIngestToken=<DATA_INGEST_TOKEN>"
💡 Pourquoi hors Git ?
C'est le seul élément de l'atelier qui n'est pas en GitOps : un secret ne va jamais dans un dépôt public. Le reste (Operator + DynaKube) est bien géré par ArgoCD.

Poste local — personnaliser puis appliquer

Votre fork contient déjà dynatrace/dynakube.yaml et argocd/dynatrace.yaml. Deux remplacements à faire dans votre IDE :

  • Dans dynatrace/dynakube.yaml : remplacez ENVIRONMENTID par l'ID de votre tenant (garde le suffixe /api).
  • Dans argocd/dynatrace.yaml (Application dynakube) : remplacez repoURL par l'URL de votre fork (comme pour podinfo).

Committez ces deux modifications, puis appliquez les Applications ArgoCD :

export KUBECONFIG=.local/atelier-kubeconfig.yaml
kubectl apply -f argocd/dynatrace.yaml
kubectl -n argocd get applications
💡 Ordre géré par ArgoCD (sync-waves)
argocd/dynatrace.yaml déclare deux Applications : dynatrace-operator (wave 0, installe l'operator + la CRD DynaKube) puis dynakube (wave 10, applique le CR). Un retry couvre le court délai de disponibilité de la CRD.
⚠️ Ressources sandbox
Le DynaKube fourni utilise le mode léger applicationMonitoring (pas de OneAgent full-stack ni de CSI driver sur chaque nœud), adapté aux 2 nœuds t3.medium. Le mode cloudNativeFullStack (commenté dans le fichier) est bien plus lourd — à réserver à un cluster plus grand.
✅ Après application
kubectl get dynakube -n dynatrace passe à Running et kubectl get pods -n dynatrace montre l'operator + l'ActiveGate en Running. Dans l'UI Dynatrace (votre tenant), le cluster Kubernetes et podinfo apparaissent au bout de quelques minutes. Vous avez maintenant Prometheus ET Dynatrace, tous deux gérés en GitOps. 🎉
